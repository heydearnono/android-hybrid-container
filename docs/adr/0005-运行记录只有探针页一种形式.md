# ADR-0005 · 运行记录只有探针页 + probe.sh 一种形式

- 日期：2026-09-18
- 状态：已采纳

## 背景

三端（Android / iOS / HarmonyOS）各自实现同一份容器规划，M5 的收口是**把三份记录并排看**。并排看得成立，
前提是三份记录的形状一样：同样的断言、同样的拼写、同样的顺序、同样的输出。

而这类记录最自然的形式（截图、手写「我看过了，没问题」）恰好都不能并排比：截图看不出 slug，
手写结论看不出哪一条没做。

## 决定

本端的运行记录**只有一种形式**：`./scripts/probe.sh` 打出的固定十六行 `<slug> PASS|FAIL|MANUAL`。

- 断言由探针页自己判，结果打进 console（`CRAB-PROBE <slug> PASS|FAIL <细节>`），经
  `WebChromeClient.onConsoleMessage` 转 logcat；页面判不了的四条由容器打的 `CRAB-NAV` 留证据
- **没有对应记录的一律 FAIL。**「没跑到」和「跑坏了」都是断言没成立
- `nav-system-scheme` 恒为 `MANUAL`（跳没跳出拨号盘只有人眼看得见），这是 pro 定的，不是没测
- 十六条之外的观察（切后台停播、销毁不崩、差异表七格）**不进这十六行**，写进 `TASKS.md`

console 转 logcat **只在 debug 构建开**（`CrabWebChromeClient(forwardConsoleToLogcat = isDebugBuild)`）：
它是调试管路，release 包不该把页面内容打进系统日志。

## 理由

- slug 拼写、顺序、固定标记全部来自 pro，端内不另定。三端一字不差才能并排看，所以端侧定义处
  （`ProbeContract`）与另外两份拷贝（探针页、`probe.sh`）之间**必须有一条自动化检查**
  ——`ProbeContractAlignmentTest` 扫文本盯住它们
- `.html` / `.js` / `.sh` 不在编译器、Spotless、lint 的任何覆盖范围里。改探针页没有任何自动化兜底，
  那条扫文本的测试是唯一的
- 也考虑过让容器把结果写成结构化文件（JSON）再回读：那要在容器里开一条页面往原生写数据的通道，
  而这一层刻意不接 JSBridge。console → logcat 是现成的、单向的、只在 debug 开的管路，够用

## 后果

- 加一条断言要同时动四处：`ProbeContract.SLUGS`、探针页、`probe.sh`、`TASKS.md`。少一处那条对齐测试就红
- 页面侧结果取该 slug 的**最后一行**（重跑时以最后一次为准），所以同一条断言只允许有一个报出处。
  第二页刻意不重复报 `nav-same-origin`，就是这个原因
- 判据靠人工按按钮，所以十六行的可信度取决于「人真的按完了才回车」。`probe.sh` 因此把清单打在屏幕上
  并停下来等，而**不代按**（见 [ADR-0001](0001-验证闭环两条命令.md)）
